# SSB (Star Schema Benchmark) on Snowflake

A small Python harness that runs the [Star Schema Benchmark](https://www.cs.umb.edu/~poneil/StarSchemaB.PDF) (SSB, O'Neil et al., rev. 3) query set against Snowflake **standard**, **interactive**, and **iceberg** tables using either a **standard** or **interactive** warehouse. It shares its harness ([`../core`](../core)) with the [`tpc-h`](../tpc-h) benchmark and offers the same setup, run, and teardown commands and options. The schema and data are SSB's.

All Snowflake object names (database, warehouses) are derived from the `SOLUTION_NAME` setting in `.env` (default `SSB`). The examples below use `SOLUTION_NAME=SSB`.

## Data source

SSB is defined as a transformation of TPC-H. The paper derives the star schema from the normalized TPC-H schema, and the reference generator ([`ssb-dbgen`](https://github.com/electrum/ssb-dbgen)) is a patched TPC-H `dbgen`. Snowflake ships TPC-H, but not SSB, in the read-only [`SNOWFLAKE_SAMPLE_DATA`](https://docs.snowflake.com/en/user-guide/sample-data-tpch) database. So `setup` **derives the SSB tables in SQL** from `SNOWFLAKE_SAMPLE_DATA.TPCH_SF<scale>`. You don't need an external data generator or a file load.

`sql/setup_source_views.sql` creates the views in `SSB_SF<scale>_SRC`, and each table format is CTAS'd from them:

| SSB table | Rows | Derived from |
|---|---|---|
| `LINEORDER` | SF × 6,000,000 | `LINEITEM` ⨝ `ORDERS` (one row per line item) |
| `CUSTOMER` | SF × 30,000 | `CUSTOMER` ⨝ `NATION` ⨝ `REGION`, first 30,000·SF keys |
| `SUPPLIER` | SF × 2,000 | `SUPPLIER` ⨝ `NATION` ⨝ `REGION`, first 2,000·SF keys |
| `PART` | 200,000 × ⌊1 + log₂ SF⌋ | `PART`, first N keys |
| `DATES` | 2,557 (1992-01-01 … 1998-12-31) | generated |
| `LINEORDER_FLAT` | SF × 6,000,000 | `LINEORDER` pre-joined with customer, supplier, and part (for the `flat` workload) |

The date table is named `DATES` (as in Apache Doris) because `DATE` is a reserved word.

Derivation rules (paper sections 2.2–2.6):

- `LO_CUSTKEY`, `LO_SUPPKEY`, `LO_PARTKEY` are folded onto the smaller SSB dimensions with `MOD`, so every fact row has a matching dimension row.
- `LO_ORDERDATE` and `LO_COMMITDATE` are `YYYYMMDD` integer keys into `DATES.D_DATEKEY`.
- `LO_DISCOUNT` (0–10) and `LO_TAX` (0–8) are whole percents.
- `LO_REVENUE = extendedprice × (100 − discount) / 100`.
- `LO_SUPPLYCOST = 0.6 × unit price` (`extendedprice / quantity`), as in `ssb-dbgen`.
- `C_CITY` / `S_CITY` are the first 9 characters of the nation, blank padded, followed by a digit 0–9 (e.g. `UNITED KI1`). The digit is a deterministic hash of the key, so repeated setups produce identical data.
- `P_MFGR` / `P_CATEGORY` reuse the TPC-H manufacturer and brand digits (`Brand#MN` → `MFGR#M`, `MFGR#MN`). `P_BRAND1` adds a deterministic suffix 1–40 (1,000 brands). `P_NAME` is the first two TPC-H colors, and `P_COLOR` is the first.
- `D_WEEKNUMINYEAR = D_DAYNUMINYEAR / 7 + 1` (the `ssb-dbgen` formula, which is what Q1.3's "week 6" means).

### Notes on the references

- **Paper inconsistencies.** The SSB paper's prose and SQL disagree for two queries. We use the values every published implementation (Doris, ClickHouse, …) uses: Q1.3 `lo_quantity BETWEEN 26 AND 35` (the prose says 36–40), and Q2.3 `p_brand1 = 'MFGR#2239'` (the prose says `MFGR#2339`, the SQL says `MFGR#2221`).
- **`ssb-dbgen`.** The repo was useful for formulas the paper leaves out: supplier cardinality 2,000·SF (fixed in its 2010 revision), the week-number formula, selling seasons and holidays, and the supply-cost formula. It also has bugs we didn't copy:
  - month names misspelled (`Augest`, `Octorber`)
  - `D_LASTDAYINMONTHFL` inverted
  - `D_DAYNUMINWEEK` shifted (Saturday = 1)
  - `P_NAME` left with four colors instead of two

  The date dimension here follows the paper's definitions.
- **Data values.** Because the data is derived from Snowflake's TPC-H sample data rather than generated by `ssb-dbgen`, the cardinalities, value domains, and filter factors match the SSB spec, but the individual values and answers differ from a `dbgen`-generated SSB dataset.

## Repo layout

This folder only holds what is specific to SSB. The CLI, execution, timing, validation, result storage and the shared SQL templates (warehouses, results table, teardown) live in [`../core`](../core) (`bench_core`); see [`../README.md`](../README.md).

```
.
├── iwssb.sh                # convenience wrapper (same as `uv run iw-ssb`)
├── pyproject.toml          # uv workspace member (depends on bench-core)
├── queries/
│   ├── original/           # 13 SSB queries (Q1.1 … Q4.3) as in the paper
│   ├── modern/             # rewritten variants (no DATES join, explicit joins)
│   └── flat/               # same queries against the denormalized LINEORDER_FLAT
├── ssb-results-1GB.json    # SF1 reference rows for optional result validation
├── sql/
│   ├── setup_source_views.sql         # SSB views derived from SNOWFLAKE_SAMPLE_DATA.TPCH_SF<scale>
│   ├── setup_standard_tables.sql      # standard tables (CTAS)
│   ├── setup_interactive_tables.sql   # interactive tables
│   ├── setup_iceberg_tables.sql       # iceberg tables
│   └── teardown_source_views.sql      # drop source-view schema
├── src/
│   ├── ssb_runner.py       # CLI entry shim
│   └── ssb/
│       └── cli.py          # SSB BenchmarkSpec (schema prefix, tables, query ids/flights, source views) + main
└── results/                # JSON + CSV per benchmark run
```

Warehouse, results-table and teardown scripts come from `../core/src/bench_core/sql/`.

## Prerequisites

- `uv` to run Python and manage the virtual environment and packages. See [uv Installation](https://docs.astral.sh/uv/getting-started/installation/).
- A Snowflake connection in `~/.snowflake/connections.toml`. It needs a role that can create databases and warehouses (the setup scripts use `SYSADMIN`) and can read `SNOWFLAKE_SAMPLE_DATA.TPCH_SF1`, `TPCH_SF10`, `TPCH_SF100`, and `TPCH_SF1000`. You can use the `snow` CLI to [set up the connection](https://docs.snowflake.com/en/developer-guide/snowflake-cli/connecting/configure-connections).
- Copy `.env.example` to `.env` and set at least `CONNECTION_NAME` (the connection name from `connections.toml`) and `SOLUTION_NAME` (used to derive all Snowflake object names).

```bash
uv sync
cp .env.example .env   # then edit CONNECTION_NAME, etc.
```

## Scales

Select the scale factor with `--scale {1,10,100,1000}`. The default comes from `DEFAULT_SCALE` in `.env`, or `10` if unset. Each scale maps to the TPC-H source schema of the same scale factor.

| Scale | LINEORDER rows | Standard schema | Interactive schema | Iceberg schema |
|---|---|---|---|---|
| `1` | ~6M | `SSB_SF1` | `SSB_SF1_IT` | `SSB_SF1_ICE` |
| `10` | ~60M | `SSB_SF10` | `SSB_SF10_IT` | `SSB_SF10_ICE` |
| `100` | ~600M | `SSB_SF100` | `SSB_SF100_IT` | `SSB_SF100_ICE` |
| `1000` | ~6B | `SSB_SF1000` | `SSB_SF1000_IT` | `SSB_SF1000_ICE` |

## Snowflake objects created

`setup --scale N` creates (or reuses) objects in `<SOLUTION_NAME>_BENCH_DB`. Use `--tables-type` and `--warehouse-type` to control what gets created. The default is `all`, or nothing when only `--save-to-snowflake` is given. Run setup separately for each scale you want to benchmark.

| Object | Type | Notes |
|---|---|---|
| `<SOLUTION_NAME>_BENCH_DB` | Database | shared across scales; created if it doesn't exist |
| `SSB_SF<scale>_SRC` | Schema | 6 views deriving SSB from `SNOWFLAKE_SAMPLE_DATA.TPCH_SF<scale>` (created whenever any tables are set up) |
| `SSB_SF<scale>` | Schema | 6 standard tables (CTAS from the source views) |
| `SSB_SF<scale>_IT` | Schema | 6 interactive tables |
| `SSB_SF<scale>_ICE` | Schema | 6 iceberg tables (`CATALOG = 'SNOWFLAKE'`, `EXTERNAL_VOLUME` from the `ICEBERG_EXTERNAL_VOLUME` setting) |
| `<SOLUTION_NAME>_BENCH_WH_LOAD` | Standard warehouse | temporary; sized for the CTAS load and dropped at the end of each table setup script |
| `<SOLUTION_NAME>_BENCH_WH_STD_<scale>` | Standard warehouse | used for the standard warehouse benchmark |
| `<SOLUTION_NAME>_BENCH_WH_INT_<scale>` | Interactive warehouse | used for the interactive warehouse benchmark; attached to the tables in the schema selected by `--tables-type`; `FALLBACK_WAREHOUSE` is `<SOLUTION_NAME>_BENCH_WH_STD_<scale>` |
| `SSB_RESULTS.BENCHMARK_RUNS` | Hybrid table | only with `--save-to-snowflake`; one row per benchmark run |
| `SSB_RESULTS.BENCHMARK_RUN_SEQ` | Sequence | generates `BENCHMARK_RUN_ID` |

The six tables in each schema are `LINEORDER`, `LINEORDER_FLAT`, `CUSTOMER`, `SUPPLIER`, `PART`, and `DATES`. `LINEORDER` and `LINEORDER_FLAT` are clustered by `LO_ORDERDATE`: every SSB query restricts or groups by time, and the paper (section 3.2) recommends a time sort. Dimensions are clustered by their key.

Warehouse sizes per scale (same as `tpc-h`):

| Scale | Load warehouse | Standard warehouse | Interactive warehouse |
|---|---|---|---|
| `1` | SMALL | SMALL | SMALL |
| `10` | LARGE | MEDIUM | MEDIUM |
| `100` | XLARGE | LARGE | LARGE |
| `1000` | XXLARGE | XXLARGE | XXLARGE |

## Usage

`./iwssb.sh` is shorthand for `uv run iw-ssb`; both accept the same arguments:

```bash
# 1. Create all table types + warehouses for a scale (default: all)
./iwssb.sh setup --scale 1
./iwssb.sh setup --scale 10

# Create only specific table/warehouse types
./iwssb.sh setup --scale 10 --tables-type iceberg --warehouse-type standard
./iwssb.sh setup --scale 10 --tables-type iceberg --target-file-size 128
./iwssb.sh setup --scale 10 --tables-type standard  # warehouses default to all

# Results table only (see "Saving results to Snowflake")
./iwssb.sh setup --save-to-snowflake
./iwssb.sh setup --recreate-results-table   # drop + recreate; existing results are lost

# 2. List databases and warehouses created for this solution
./iwssb.sh list

# 3. Run the 13 SSB queries
# Defaults: --warehouse-type interactive, --tables-type standard, --workload original
./iwssb.sh run
./iwssb.sh run --warehouse-type interactive --tables-type interactive --scale 10
./iwssb.sh run --warehouse-type standard --tables-type iceberg --scale 10
./iwssb.sh run --warehouse-type standard --tables-type standard --scale 100 --workload modern
./iwssb.sh run --warehouse-type standard --tables-type standard --scale 100 --workload flat

# Single query / subset / whole flights / repeated runs
./iwssb.sh run --query 3.4
./iwssb.sh run --queries 1.1,2.3,4.3
./iwssb.sh run --queries 2,4         # all of flights Q2.x and Q4.x
./iwssb.sh run --repeats 5           # best of 5 executions per query
./iwssb.sh run --iterations 3        # 3 full workload passes

# Average mode: 1 warmup run + N measured runs, report average
./iwssb.sh run --avg
./iwssb.sh run --avg --repeats 5

# Also save the run into the Snowflake results table
./iwssb.sh run --warehouse-type standard --tables-type standard --scale 100 --save-to-snowflake

# 4. Optional cleanup
./iwssb.sh teardown --scale 10                          # drop all schemas (incl. _SRC) + warehouses for scale 10
./iwssb.sh teardown --scale 10 --tables-type iceberg     # drop only the iceberg schema
./iwssb.sh teardown --scale 10 --warehouse-type standard # drop only the standard warehouse
./iwssb.sh teardown --scale 10 --drop-database           # also drop the entire database

# Override connection, database, schema, or warehouse (any subset)
./iwssb.sh run --connection PM --database SSB_BENCH_DB --schema SSB_SF100 --warehouse SSB_BENCH_WH_STD_100
```

Query ids are `1.1`–`1.3`, `2.1`–`2.3`, `3.1`–`3.4`, and `4.1`–`4.3`. `Q2.1`, `2_1`, and a bare flight number (`3`) are also accepted.

Each run writes `results/run_<warehouse_type>-<tables_type>_sf<scale>_<workload>_<UTC-timestamp>.json` and `.csv`. These contain per-query rows (status, row count, client elapsed, server elapsed from `INFORMATION_SCHEMA.QUERY_HISTORY_BY_SESSION`, query_id, error) and a summary (connection, database, schema, warehouse, warehouse size, timing stats).

## Workloads

| `--workload` | Description |
|---|---|
| `original` (default) | The 13 queries exactly as in the SSB paper (comma joins against `DATES`, `OR` predicates) |
| `modern` | Same results. `LO_ORDERDATE` is a `YYYYMMDD` key, so every date-dimension predicate becomes a range on the fact table's clustering key and `d_year` becomes `FLOOR(lo_orderdate / 10000)`. This drops the `DATES` join entirely and allows partition pruning. The rewrite also uses explicit `JOIN … ON` and `IN` lists. Q1.3's `d_weeknuminyear = 6 AND d_year = 1994` is `19940204 … 19940210`. |
| `flat` | Same predicates as `modern`, run against the denormalized `LINEORDER_FLAT` table (no joins), like the [Apache Doris SSB-Flat](https://doris.apache.org/docs/3.x/benchmark/ssb) test |

All three workloads were verified to return identical result sets on standard, interactive, and iceberg tables at SF1.

## Saving results to Snowflake

Pass `--save-to-snowflake` to `run` to also store the run in the hybrid table `<SOLUTION_NAME>_BENCH_DB.SSB_RESULTS.BENCHMARK_RUNS`. Create the table first with `setup --save-to-snowflake`. `setup --recreate-results-table` drops and recreates the table and its sequence. Rows are written using the standard warehouse `COMPUTE_WH` (hybrid tables can't be written through an interactive warehouse); set `RESULTS_WAREHOUSE` in `.env` to use a different one. The columns are identical to the `tpc-h` harness (`BENCHMARK_RUN_ID`, `BENCHMARK_RUN_TS`, run type columns, summary stats, `RESULTS_JSON`).

## Result validation (SF1)

When you run with `--scale 1`, each successful query is checked against the reference rows in `ssb-results-1GB.json`. The file defines one reference row per query (`Q1.1` … `Q4.3`). Validation passes if that row appears in the result set. Matching rules are the same as in `tpc-h`:

- case-insensitive column names
- trailing blanks ignored
- numeric tolerance

The process exit code is `1` if any query fails execution or validation.

The reference values were produced by this harness on Snowflake SF1 data derived as described above. They are not published SSB answers, which come from `dbgen`-generated data. They were cross-checked across all three workloads and all three table formats. The result row counts match published SSB SF1 results (e.g. Q2.1 = 280, Q3.1 = 150, Q3.2 = 600, Q3.4 = 4, Q4.1 = 35, Q4.2 = 100). Q4.3 returns 322 rows (≈ 2 years × 10 cities × 40 brands with sparse coverage).

|---|---|---|

| Scale | `DEFAULT_SCALE` in `.env` (fallback `10`) | `--scale` on `setup`, `run`, `teardown` |
| Warehouse type | `interactive` | `--warehouse-type` on `setup`, `run`, `teardown` |
| Tables type | `standard` (run) / `all` (setup/teardown) | `--tables-type` on `setup`, `run`, `teardown` |
| Workload | `original` | `--workload` on `run` |
| Database | `<SOLUTION_NAME>_BENCH_DB` | `--database` on `run` |
| Schema | `SSB_SF<scale>` / `SSB_SF<scale>_IT` / `SSB_SF<scale>_ICE` | `--schema` on `run` |
| Warehouse | `<SOLUTION_NAME>_BENCH_WH_INT_<scale>` or `<SOLUTION_NAME>_BENCH_WH_STD_<scale>` | `--warehouse` on `run` |

## Notes

- Interactive warehouses require a standard fallback warehouse, so `--warehouse-type interactive` always creates the standard warehouse too. The interactive warehouse is attached to whichever schema `--tables-type` selects. With `all`, it is attached to the interactive tables.
- Iceberg tables require an external volume. Set `ICEBERG_EXTERNAL_VOLUME` in `.env` to a volume name, or `auto` to use the account-level default.
- `client_elapsed_s` is wall-clock time around `cur.execute` + `fetchall`. `server_elapsed_s` is `TOTAL_ELAPSED_TIME` from query history.
- Each query runs `--repeats` times (default 3) and the **best** time is kept. With `--avg`, one warmup run is followed by `--repeats` measured runs, and the **average** is reported. The result cache is disabled for the session.
